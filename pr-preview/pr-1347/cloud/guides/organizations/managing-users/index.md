# Manage Users


> Add, create, edit, and remove the people in an organization, change their roles, and understand what each action revokes and what it bills.



The Users page is where administrators manage the people in an organization. It lists the organization's members and carries the actions that put people into the organization, change what they can do, and take them out. This guide covers each action, who can run it, and what it changes.

To bring in people who do not have an account yet, or to let a group join without administrator action, use [Invite Users](/pr-preview/pr-1347/cloud/guides/organizations/inviting-users/). For what a user account is and how membership and roles combine, read the [Users concept](/pr-preview/pr-1347/cloud/concepts/identity-and-security/users/).

## Permissions

Each action needs a permission in your current organization. The server also checks your role for some actions, so holding the permission through another role is not always enough.

| Action | Permission | Also required |
| --- | --- | --- |
| Open the Users page | View All Users | None |
| Create a user | Create User | None. Organization Admin and Provider Admin hold it by default. |
| Add an existing user | Add User to Organization | You are an Organization Admin or owner of the organization, a Provider Admin, or an Organization Admin or owner of its parent organization. |

Provider roles, such as Provider Admin, are deployment-wide. Only a Provider Admin can grant or clear them.

## Find members

The Users page shows the people with a live membership in the selected organization, 10 to a page by default and at most 100. A Provider Admin can switch the scope to every organization.

| Behavior | Detail |
| --- | --- |
| Default list | Active accounts only. People who were created or invited but have not yet signed in (status Pending) and deactivated accounts are hidden until you apply a filter. |
| Default order | Most recent sign-in first. Order by sign-in time or creation time. |
| Search | Case-insensitive substring match on email, first name, and last name. |
| Filters | Role (include or exclude a role) and deleted or not deleted. |
| Columns | Name, email, status, organization roles, provider roles (Provider Admins and holders of Assign User Roles), created, last active, and counts of teams and organizations. |

Last active is the time of the person's most recent sign-in, not a live connection.

## Add an existing user

**Needs:** Add User to Organization, plus the role check in the table above.

Use this for someone who already has a Layer5 Cloud account. Search for the person, then choose the organization, and optionally the teams and organization roles they receive. The search covers every active, non-anonymous account on the deployment, not only your organization, and an empty search returns nothing.

Adding makes the person a member of the organization with **no role**. Roles and teams are separate steps that run after the membership is created. If a role or team step fails, the membership stays and the failure is reported. Adding someone who is already a member changes nothing.

Layer5 Cloud sets no seat limit on adding people. Billing counts members separately. See [Billing and seats](#billing-and-seats).

## Create a user

**Needs:** Create User.

Use this to create an account for a person who has not registered. You supply a first name, last name, and email address, all required.

Layer5 Cloud creates the account with the email address already verified and sends the person an **Account Setup** email. The link in that email is valid for 720 hours (30 days) and opens a page where the person sets a password. The account's status is Pending until they sign in.







<div class="alert alert-custom" style="border-color: #EBC017;" role="alert">
  <h4 class="alert-heading" style="color: #EBC017;">Creating a user does not add them to an organization</h4>
  
      The create form offers organization and role fields, but the account is created without them. The new user belongs to no organization and holds no roles until you add them. After creating the account, <a href="/pr-preview/pr-1347/#add-an-existing-user">add the user to the organization</a> and assign roles.
  
</div>



If the setup email cannot be sent, the request fails with `Failed to send "Account Setup" email`. The address must be a valid email; the identity provider rejects malformed addresses.

## Edit a profile

**Needs:** Update User Profile in an organization you share with the person.

Organization Admins can edit the profile of members of their organizations; Provider Admins can edit anyone. Edits to another person's profile are refused with `user is not authorized to administer this account` when you share no organization with them, and the message is the same whether the account exists or not.

The email address is restricted. A Provider Admin can change it; an Organization Admin who submits a different email is refused with `user is not authorized to change the e-mail address of this account`. Changing an email address marks the new address unverified and sends a verification message, and the person signs in with the new address once it is verified.

A person edits their own profile in [account settings](/pr-preview/pr-1347/cloud/guides/account/managing-your-account/). Granting badges is covered in [Assign User Badges](/pr-preview/pr-1347/cloud/guides/organizations/assigning-user-badges/).

## Change a member's roles

**Needs:** Assign User Roles or Assign Roles to Organization members, and a role check as shown in the permissions table.

Roles control what a member can do inside the organization. To make someone an administrator, give them the **Organization Admin** role; to take administration away, remove it.

- **Roles you submit replace the roles the member holds.** The list is the complete set for that scope, so an empty list removes every role in the scope. Removing roles never ends the membership.
- **Provider roles cannot be granted inside an organization or a team.** A request that lists one is refused with HTTP 403 for every caller, a Provider Admin included, and no part of the request is applied. Provider roles are granted only through the provider role assignment.
- **Team scope accepts only Team Admin.** See [Manage Teams](/pr-preview/pr-1347/cloud/guides/organizations/managing-teams/).
- **A request is checked before anything is written.** If one row in a batch is refused, none of the rows are applied.
- **Layer5 Cloud does not stop you removing the last administrator.** An organization's owner keeps administrator access through ownership, but other administrators can be removed, including the last one. Confirm another administrator exists before you remove the role.

Roles, their permissions, and the defaults are listed in [Roles and Permissions](/pr-preview/pr-1347/cloud/reference/default-permissions/).

## Remove a user from an organization

**Needs:** Remove User from Organization, and Organization Admin of the organization or Provider Admin.

Removal takes a person out of the organization but leaves their account intact. Remove people one at a time from the row action, or select several and remove them together; bulk removal issues one removal per person, in order.

Removal acts on the organization currently selected in your session. Check the organization switcher before you remove anyone.

### What removal ends

Removing a member ends every access-bearing relationship they hold **inside that organization**, as a single operation:

* **Their organization membership**, together with the organization [roles](/pr-preview/pr-1347/cloud/reference/default-permissions/) attached to it.
* **Their membership in that organization's [teams](/pr-preview/pr-1347/cloud/concepts/identity-and-security/teams/)**, together with the team roles attached to those memberships.

Permissions reach a user through the roles carried on those memberships. A [keychain](/pr-preview/pr-1347/cloud/concepts/identity-and-security/keychains/) granted by a team role is revoked by the removal just as an organization role's keychain is, so a removed member holds no [keys](/pr-preview/pr-1347/cloud/concepts/identity-and-security/keys/) in the organization by either route.

Removal does **not** affect:

* The person's Layer5 Cloud account, which continues to exist.
* Their membership in any other organization.
* Designs, environments, and other resources they created, which remain in the organization.
* The audit trail, which records who removed whom.







<div class="alert alert-custom" style="border-color: #EBC017;" role="alert">
  <h4 class="alert-heading" style="color: #EBC017;">Shared teams lose the member everywhere</h4>
  
      A team can be mapped to more than one organization. Removing a member from one organization ends their membership in every team mapped to it, including a team they use through another organization they still belong to. Add them back to that team afterward.
  
</div>



### Guards and outcomes

| Situation | Result |
| --- | --- |
| The person is the organization's owner | Refused with `Organization owner cannot be removed`. Ownership cannot be transferred, so the owner stays a member for the life of the organization. Promote another member to Organization Admin if you need a second administrator. |
| An owner tries to remove themselves | Refused: owners cannot leave. Delete the organization instead. |
| An administrator removes themselves, and is not the owner | Allowed. |
| The person was never a member | `no organization membership to remove`. |
| The same removal is repeated | Succeeds and changes nothing. |
| One person in a bulk selection is refused | Only that row fails. The result names each refused person with the reason, for example `Failed to remove 1 of 3 user(s): name@example.com (reason)`, and the others are removed. |

Removal is not reversible from the Users page. To restore access, add the person again and reassign their roles and team memberships. Neither returns on its own. The confirmation reports only that the member was removed and does not list the team memberships that ended with it, so review the member's teams first if you need a record.

## Delete an account

Deleting an account removes a person from Layer5 Cloud entirely, in every organization. It is a Provider Admin capability. Organization Admins remove members from their own organization instead; they cannot delete accounts.







<div class="alert alert-custom" style="border-color: #EBC017;" role="alert">
  <h4 class="alert-heading" style="color: #EBC017;">Account deletion from an organization's Users page does nothing</h4>
  
      The Users page shows the delete action to holders of Delete User, but a request issued from a single organization&rsquo;s page reports success without deleting anything. Deletion takes effect only when a Provider Admin runs it with the all-organizations scope. Use removal to end someone&rsquo;s access to your organization.
  
</div>



Account deletion is refused when the account holds credentials designated to an organization that has no other owner or Organization Admin to receive them; promote another administrator or release the credentials first. A person deletes their own account from [account settings](/pr-preview/pr-1347/cloud/guides/account/managing-your-account/).

## Billing and seats

Removing a member stops them counting toward billing, and adding one starts it. A subscription's billable user count is the number of distinct members with a live organization membership and an active account, excluding members whose only role is Academy Learner, and never below the plan's minimum. A member added with no role is not counted. The count adjusts the subscription quantity; it does not block anyone from joining. See [how the billable user count works](/pr-preview/pr-1347/cloud/guides/account/managing-subscriptions/#how-the-billable-user-count-works).

## Events

Adding, creating, removing, editing, and role changes each write an audit event that names the person who acted and the person affected, for example `<actor> removed <person> from organization`.
